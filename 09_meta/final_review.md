## エグゼクティブサマリー(まず結論から)

**Web デザイナー視点(100点満点換算): 76点 / 100**
- ブランドコンセプトの統一性は秀逸。ダーク・ストイック系のトンマナが12ページ全体で一貫している。
- 一方で「**初見ユーザーへの説明不足**」「**信頼要素の弱さ**」「**コンバージョン直前のサポート不足**」が明確な課題。
- 課題作品としては **B+ 〜 A-**(課題評価ではなく仮想的な実務評価)。実務リリースには信頼要素・コンテンツの肉付けが必要。

**AI 開発専門家視点(100点満点換算): 84点 / 100**
- マルチエージェント設計、ドキュメントの構造化、自己採点ループはほぼ模範解答。
- 工数の使い方(画像候補の事前収集が結果的に無駄になった等)に**改善余地が大きい**。
- 「**なぜそのプロンプトを書いたのか**」の意図記録があれば次回以降の再現性が劇的に上がる。
- 課題プロセスとしては **A**。AI 講座の演習成果としては高い完成度。

**結論**:**完成度より、ここから何を学ぶか**が重要。下記、両視点で計20の評価軸を設定し、各項目で「**ここはこうすべきだった**」を具体的に挙げます。

## 採点と詳細フィードバック(Web デザイン編)

### W1. コンセプト・ブランド表現 — **9 / 10**

**良い点**
- 「**北アルプスの麓から、本物の健康を研究する**」という1行のコピーがサイト全体の指針として完全に機能している
- TOP の Split Composition「NATURE × BODY」は**抽象的なブランド宣言を視覚で言い切った**素晴らしい構図
- 章番号(MISSION 01 / CONCEPT 02 …)と地理座標装飾(LAT 36.2°N / LON 137.9°E)で「研究レポート風」の独自世界観を全ページに展開できている
- カラー比率(黒80-90% / ゴールド3-5% / 赤1-3%)が全ページで守られていて、ブレがない

**改善できた点**
- 「研究 = LAB」を視覚で語る要素が**比喩レベルに留まっている**。実際の Phive Clubs や fitlab は「データの可視化」「グラフ」「科学的な計測値表示」など**より具体的な"研究"のビジュアル**を入れている。あなたのサイトは「研究と謳っているが、研究の証拠ビジュアルは抽象に留まる」状態
- 例えば「**会員の健康データの推移グラフ**(ダミーOK)」「**研究員プロフィール(白衣+資格)**」「**年間の検査・分析実施件数**」みたいな"ラボ感"の数値・図版があれば、ブランドの説得力が一段上がっていた

### W2. 情報設計・サイトマップ — **7 / 10**

**良い点**
- 12ページ構成は、4事業 × 詳細 + 共通ページ(ABOUT/STORES/STORIES/RECRUIT/COMPANY/CONTACT)という**ロジカルな分割**
- SERVICES 一覧 → 各事業詳細という二段階構造はユーザーが「全体を把握 → 興味あるもの深堀り」のフローを取りやすい

**改善できた点**
- **12ページは多すぎる**(参考の Phive Clubs は5〜6ページ程度)。SERVICES一覧は実質、TOPの事業紹介セクションと内容が重複しがち。**SERVICES一覧を廃止して、4事業詳細ページだけにする**選択肢があった
- COMPANY と RECRUIT の重複領域(代表メッセージなど)が薄く、それぞれが「義務的に存在するページ」感を漂わせている。**RECRUIT を ABOUT 内のセクションに統合**するなど、ページ統合の余地あり
- STORIES がブログ的な機能を持つが、3〜6件の記事しかないと**過疎感**が出る。最初は STORIES なしで、コンテンツが10件以上溜まってから公開する戦略もあり得た

### W3. ナビゲーション設計 — **7 / 10**

**良い点**
- 主要5項目(ABOUT / SERVICES / STORES / STORIES / RECRUIT)+ CTA(体験予約)の構成は標準的で理解しやすい
- ハンバーガーメニュー(モバイル)とPC横並びの切り替え対応

**改善できた点**
- **SERVICES のドロップダウンがない**。SERVICES クリック → 一覧ページ経由で各事業へ、という遷移は**1クリック余分**。ホバー時に「GYM / NUTRITION / FOODS / SUPPLEMENTS」のメガメニューを出すべき
- COMPANY と CONTACT がフッター送り(ヘッダーから消える設計)になっている可能性がある。**COMPANY はヘッダー右側の細字でも残す**のがコーポレートサイトの標準。CONTACT は CTA とは別に「文章で問い合わせ」窓口として目立たせる必要あり
- パンくずリスト(`TOP > SERVICES > GYM` のような表示)が実装されていない。階層が深いサイトでは必須

### W4. ファーストビューの完成度 — **7 / 10**

**良い点**
- 「Split Composition / NATURE × BODY」は**強烈に印象に残るデザイン**で、3秒以内に「ただのジムサイトじゃない」と認識させる力がある
- カラーリング・タイポグラフィの完成度は高い

**改善できた点**(ここが最重要)
- **「これは何のサイトか」が分かりにくい**。`RESEARCH THE TRUTH OF HEALTH` だけでは「ジム」「栄養指導」「冷凍食品」「サプリ」という事業内容が一切伝わらない。初見ユーザーは「これは何屋?」と1秒迷う
- 改善案:Hero 直下に**1行サマリー**を追加すべき。例:
  > 「**24時間ジム × パーソナル / 栄養指導 / 冷凍宅配 / サプリの4事業で、長野発の健康習慣を設計**」
- これがあれば「**ブランドの世界観 + 実態の事業内容**」の両方が3秒で伝わる
- もう1つ:体験予約 CTA の隣に「料金プランを見る」「サービス一覧を見る」のセカンダリCTAを置くべき。今は「予約 OR スクロール」しか選択肢がなく、迷ったユーザーが離脱するリスクがある

### W5. コンバージョン誘導設計 — **7 / 10**

**良い点**
- GYM ページの「Hero → 施設 → 料金 → トレーナー → フロー → FAQ → CTA」というファネル構成はテンプレート的に正しい
- 体験予約 CTA をページ内に **5回以上**繰り返し配置している(スクロール途中で離脱しない設計)
- 料金プランで STANDARD を「OUR PICK」とラベル付けして誘導(ロックインバイアスの活用)

**改善できた点**
- **「体験予約」のクリック先が CONTACT フォーム**だが、これだとお問い合わせ全般と混在する。**`/trial/` や `/booking/` という専用ページ**を作って、体験予約専用フォームにすべき。「お問い合わせ種別を選んでください」を毎回見せられるのは、予約意欲が下がる
- **限定性・希少性の演出が弱い**(高級ジムサイトの定番テクニック)。例:「松本本店 残席わずか」「定員限定◯名まで」「本日お問合わせで初月無料」など
- **チャットボットが無い**。プレミアム志向のジムは Tawk / Drift などで「24時間質問対応」を演出している。これが無いだけで信頼度が落ちる
- **離脱フォーム(exit-intent popup)が無い**。マウスがブラウザ外に向かったら「**まだお迷いなら…**」と引き止める仕掛け
- **再訪促進が無い**。クッキーで初回訪問者を識別、2回目訪問時にだけ「初回限定オファー」を出すなど

### W6. ビジュアル階層・タイポグラフィ — **8 / 10**

**良い点**
- 3フォント体制(Bebas Neue / Noto Sans JP / Inter)を**役割別に厳密に運用**している
- 章番号調整の修正後は、視覚階層(主見出し > 章番号 > 本文 > メタ)が機能している
- 余白の取り方が大胆(Snow Peak 的)で、安っぽくならない

**改善できた点**
- **行間(line-height)のバラツキ**: 日本語本文の line-height が場所によって異なる。1.5 〜 1.8 のどちらかに揃えて、長文ブロックは 1.8 にすべき
- **数値の揃え方**: 料金「¥8,800」「¥22,800」のような数字の桁を揃えて表示すべき(tabular-nums の CSS で実現可能)
- **強調表現の弱さ**: 重要な単語(「**本物**」「**研究**」「**30年**」)に下線・色変えなどの装飾が無い。読み流しを防ぐマーカーが少ない

### W7. トラスト要素 — **5 / 10**(最弱項目)

**良い点**
- 会員の声を3件掲載
- 店舗3拠点を実在風に提示
- FAQ 5件で疑問を先制対応

**改善できた点**(ここが2番目に重要な改善ポイント)
- **「研究」を謳いながら、研究の証拠が薄い**。具体的に欲しい要素:
  - 顧問医師・栄養士の**実名+顔写真+経歴**
  - **大学・研究機関との連携**ロゴ(信州大学医学部とコラボ等の設定)
  - **取得認証マーク**(JSPO-AT、健康運動指導士など)
- **数字が弱い**: 「会員数 1,200名」「累計減量実績 12,000kg」みたいな**累計実績の数字**が無い
- **メディア掲載実績**が無い: 「日経新聞掲載」「BRUTUS取材」みたいな第三者評価ロゴ
- **会員の声がたった3件**: 30〜50件あって初めて「多くの人に支持されている」と感じる。3件だと「ぎりぎり用意した感」が出る
- **写真がストックフォトで顔の見える人物が少ない**: 実名・顔出しの実在性が信頼の最強パーツ。本番ではスタッフの実物写真への差し替えが必須

### W8. アクセシビリティ — **8 / 10**

**良い点**
- 全画像に alt 属性(Reviewer Agent が確認済み)
- セマンティック HTML(`<header>`, `<main>`, `<section>`, `<footer>`)を適切に使用
- `prefers-reduced-motion: reduce` で動きを止められる配慮
- WCAG AA 準拠のコントラスト比

**改善できた点**
- **フォーカス可視化(focus-visible)が標準的すぎる**: 黒背景+ゴールドアクセントなのだから、フォーカス枠も**ゴールドの2px破線**くらいで明示すべき
- **スキップリンク**は実装済みだが、視覚的に分かりにくい(隠れている)。タブキー押下時の見え方を確認すべき
- **CONTACT フォームのエラーハンドリング**: バリデーションエラー時に `aria-invalid` と `aria-describedby` の連携が記述されていない可能性。スクリーンリーダーユーザーにエラーが伝わらない
- **キーボードナビゲーションのテスト**: ハンバーガーメニュー開閉、FAQ アコーディオン、フォーム送信などを Tab キーだけで完了できるか手動確認すべき

### W9. レスポンシブ・デバイス対応 — **7 / 10**

**良い点**
- 4ブレークポイント(1280 / 1024 / 768 / 480)で設計
- ハンバーガーメニュー、カラム数の切り替え、画像サイズの最適化など標準的な対応

**改善できた点**
- **モバイルのファーストビュー**: Split Composition は PC 向けの構図。モバイルでは縦に2分割すると窮屈になりやすい。モバイルだけ別構図(山岳画像 → キャッチ → 人物画像 の順に縦並び)を検討すべき
- **タッチターゲット**: ボタンや文字リンクが**44px×44px 以上**を確保しているか要確認(Apple HIG の最小推奨)
- **ヒーローの動画背景がモバイルでは静止画**: これは正解だが、**動画ロード待ち時間でカクつく**問題が起きやすい。`<video preload="none">` の指定 + ポスター画像の表示 を確実にすべき
- **iOS Safari での 100vh 問題**: モバイル Safari は URL バーで vh が変化する。`min-height: 100svh` (small viewport units)を使うべき(Vanilla JS でフォールバック実装も推奨)

### W10. コンテンツの質・量バランス — **6 / 10**

**良い点**
- 各ページに最低限の情報は揃っている(ヒーロー + 詳細 + CTA)
- ダミーデータの存在を実装ログで明示している(透明性◎)

**改善できた点**
- **STORIES が薄い**: 6件程度では「コンテンツ豊富なメディア」感が出ない。**最低15件、理想は30件**は欲しい
- **FAQ が5件は少なすぎる**: ジムサイトの FAQ は20〜30件あるのが普通(設備、料金、退会、シャワー、駐車場、子供連れOK?など)
- **代表メッセージがダミー**: 課題なら仕方ないが、本番なら最重要要素の一つ。動画でメッセージを伝えるなど、力の入れ方で差が出る部分
- **採用ページの情報不足**: 募集職種、給与レンジ、福利厚生、選考フロー、インタビュー(実在の社員)— このどれかが欠けると「採用に本気じゃない」と見られる

## 採点と詳細フィードバック(AI開発編)

### A1. 企画書の構造化 — **10 / 10**(最高評価)

**良い点**(全部)
- 9カテゴリ40+ファイルへの分割は**模範的**。Claude Code でこれだけ整然とした企画書は初めて見た
- 「**全部読む**ではなく**必要な分だけ読む**」原則を明文化(00_README.md)し、各エージェントの読み込みファイルを指定している
- 1ファイル1責務の徹底(concept は concept、design は design)で、読みたい部分だけピンポイントで読める
- ファイル名の命名規則が一貫(`01_brand/`, `04_pages/services_gym.md` 等)で、AIが推測でアクセスできる

**改善できた点**(あえて言うなら)
- **更新履歴・バージョン管理が無い**: 各MDの先頭に `Last updated: 2026-05-05` のようなメタ情報があれば、AI が「これは古い」と判断しやすい
- **クロスリファレンスが弱い**: `services_gym.md` から `services_pricing.md` への参照が「`参照: 02_strategy/service_pricing.md`」みたいに統一フォーマットだとなおよし

### A2. マルチエージェント設計 — **9 / 10**

**良い点**
- Designer / Coder / Reviewer の3役分担は**教科書通りの最適解**
- 各エージェントに「必読ファイル一覧」「タスク」「アウトプット形式」「評価基準」を明示
- handoff_format.md でエージェント間の引き継ぎ書式を厳密に定義 → Coder が「Designerの意図」を解釈で迷わない
- self_refine_criteria.md による自己採点ループ(40点未満なら再実装)はループの暴走を防ぐ良い設計

**改善できた点**
- **PM Agent が定義されているのに使われていない**: pm_agent.md があるが、実プロジェクトでは PM の役割を私(orchestrator)とユーザーが兼任してしまった。**PM Agent を最初に起動して、タスク分解と各エージェントへの指示書(02_designer_brief.md など)を作らせる**フローが正規ルート
- **エージェント間のフィードバックループが片方向**: Coder → Reviewer のレビューはあるが、**Coder → Designer に「この仕様だと実装が難しい」と差し戻すパス**が定義されていない。実務だと頻出する状況
- **役割の粒度を変える余地**: 例えば「アクセシビリティ専任のレビュアー」「SEO専任のチェッカー」を入れる選択肢があった

### A3. プロンプト精度 — **8 / 10**

**良い点**
- 「**不変制約**」を明示するスタイル(色・フォント・コピーは変更不可)が一貫
- 「**Stop and report after N**」で agent の暴走を防止
- 「**◯◯はやらない**」「◯◯は変えない」の禁止リストを併記

**改善できた点**(ここが具体的に学びの宝庫)

#### 失敗例1: 章番号フォントサイズの問題
- 私が Designer Agent に **「章番号は現状のままでOK(意図的に小さく抑えている)」と明示的に書いた**
- ユーザーが「小さすぎる」と気付き、修正依頼が必要になった
- **教訓**: AI に「変えるな」と指示するときは、**変えないことの根拠が確実か**を疑うべき。「現状OK」と書くと、AI は判断を放棄する

#### 失敗例2: 画像候補の事前収集が無駄になった
- ユーザーに「画像を集めておくと役立つ」と提案 → 30枚以上収集 + ★マーキング作業
- 結果、Designer Agent が**文脈の中で別の画像を選び、ユーザーはそちらを採用**
- **教訓**: AI が選定するフェーズの前に人間が「素材を絞り込む」のは**情報損失**を生むことがある。AIに先に選ばせ、不満があれば候補を提示する順が効率的

#### 失敗例3: orchestrator への「ページ数」指示
- 第2バッチで「残り8ページ」と指示したが、実際は9ページだった(SERVICES一覧を私が見落とし)
- orchestrator が「実際は9ページですよ」と訂正してくれた
- **教訓**: 数値を含む指示は、**明示リストで列挙**するのが安全(「8ページ」ではなく「ページ名9つを列挙」)

#### 良かった例
- DECISION_NOTES.md に「**維持すべき不変の制約**」セクションを設けた → Designer Agent / Coder Agent 両方がここを参照して、ブランド一貫性が保たれた
- 「Self-score with criteria, fail if <40」のループ → 一発合格率が高かった

1. **「AIに任せる前に人間が情報を絞り込みすぎない」**

# 第五部:なぜ Reviewer Agent は気づけなかったのか(評価設計の構造的限界)

> 重要な問い:Designer / Coder Agent は自己採点で **44.6/50 という高評価**(40点で合格、50点満点中)を出した。
> にも関わらず、本レビュー(第一部・第二部)では**多数の改善点**が見つかった。
> このギャップは「課題だからクオリティを下げた」では説明できない構造的原因がある。
>
> この章は ALPS LAB プロジェクトから得られた **AI 開発における最も重要なメタ学習**を記録する。

## ギャップの正体:評価が「外部視点」を欠いていた5つの層

| 層 | 内容 | 結果として見えなかったもの |
|---|---|---|
| **第1層:評価基準の範囲が狭い** | self_refine_criteria.md は「ブランド一貫性 / コード品質 / パフォーマンス / a11y / レスポンシブ」の5軸のみ | トラスト要素、初見ユーザーへの伝達力、コンバージョン誘導の最適性が**評価対象外**だった |
| **第2層:評価基準の深さが浅い** | 「会員の声3件」が**仕様**として書かれていれば、Reviewerは「仕様を満たしている = OK」と判定 | 「業界水準は30件、3件では『取って付け感』が出る」という**仕様自体への疑問**が出ない |
| **第3層:スコープが1ページ単位** | Reviewer は各ページを個別評価 | 「12ページは多すぎる」「SERVICES一覧と TOP の事業紹介が内容重複」のような**サイト全体構造の問題**が原理的に検出不可能 |
| **第4層:インセンティブが「合格 / 不合格」** | 40点超えたら採点ストップ。50点を目指す動機が無い | 「あと2点改善するには何が必要?」という**最適化視点**が欠けた |
| **第5層:視覚情報が無い** | Reviewer はコードだけ読む(text-only)。本レビューは WebFetch で実物を見ている | 「フォントサイズが視覚的に小さすぎる」「画像と見出しのバランス」のような**視覚的問題**が検出不可 |

→ 結論:**Reviewer Agent が機能不全だったのではなく、Reviewer に与えられた基準・スコープ・入力情報が「外部視点」を構造的に欠いていた**。AI の能力の問題ではなく、**評価設計の問題**。

## ここから得られる5つの学び

### 学び 1:Reviewer は「与えられた基準」しか見ない

評価項目に無いものは原理的に検出不能。次回プロジェクトでは:
- 評価基準を**実装着手前ではなく、業界ベンチマークを調査してから**決める
- 業界の標準的な評価軸(UX、コンバージョン、トラスト、SEOなど)を漏れなく含める

### 学び 2:ロールの数が足りなかった

Designer / Coder / Reviewer の3役では視点が偏る。理想形:

```
[既存] Designer    ← デザイン作成
[既存] Coder       ← 実装
[既存] Reviewer    ← コード品質チェック
[追加] Critic      ← UX・コンバージョン・トラスト視点での批評
[追加] BrandGuard  ← ブランド整合性の最終確認
[追加] PersonaSimulator ← ペルソナの立場で「私は申し込む?」を疑似評価
```

**Critic Agent** は「**業界ベンチマークと比較して何が足りないか**」を専門に問う役割。
本レビュー(第一部のW7トラスト要素=5/10など)で発見された問題の大半は、Critic Agent があれば実装段階で気付けた可能性が高い。

### 学び 3:「合格基準」と「卓越基準」を分ける

self_refine_criteria.md は **合格基準(40点)** に最適化されていた。これは正しい設計。
ただし、**卓越基準(50点を目指す基準)** を別ファイルで定義しておけば、合格後に「もう一段上がるには?」を自動で問えた。

```
合格基準(必須クリア)
├─ 仕様適合性
├─ コード品質
├─ パフォーマンス
├─ アクセシビリティ
└─ レスポンシブ

卓越基準(任意の最適化)← 追加すべき
├─ 業界ベンチマーク比較(参考サイト3つに対して何が劣るか)
├─ ペルソナ視点(ペルソナA/B/Cの何名がCVするか)
├─ トラスト要素の充実度
├─ コンバージョンファネル最適化
└─ コンテンツの量と質のバランス
```

### 学び 4:視覚情報を AI に渡す手段を組み込む

Reviewer がコードしか読めなかったのは構造的限界。次回は:
- 実装後にスクリーンショットを撮る(Playwright / Puppeteer など)
- スクリーンショット + コードの両方を Critic Agent に渡す
- Vision モデルで視覚的問題を検出

これだけで「フォントサイズが小さすぎる」「色の対比が弱い」「画像が引き伸ばされている」などが**実装段階で**検出できる。

### 学び 5:自己採点には本質的な限界がある(AI 固有の問題ではない)

これは AI に特有の問題ではなく、**人間も同じ**。プロのデザイナーでも自分の仕事を100%客観評価することは不可能。**身内採点は構造的に甘くなる**。

→ 品質保証の本質は「**外部視点をシステムに組み込むこと**」。具体的には:
- 別ロールの AI(Critic Agent)
- 別人間(友人や講師)
- 別ツール(Lighthouse, axe-core, PageSpeed Insights)

これらを **複数組み合わせる**ことで、初めて自己採点の限界を補える。

## メタ的な意義:この発見が今後のあなたの武器になる

「**自分が評価基準を設計しないと、AI は基準の外を見てくれない**」という気付きは、**AI 開発の最重要原則の一つ**です。

具体的には、今後のプロジェクトで以下のように活きます:

1. **「AI に任せれば自動的に高品質になる」という幻想を捨てる**
   → 評価基準 = AI の視野 と理解し、視野を意図的に広く設計する

2. **「Reviewer の合格 = 完成」ではなく「合格 = スタートライン」と捉える**
   → 必ず外部視点(別ロール / 人間 / ツール)で再チェックする工程を組み込む

3. **AI に "あえて批判的な視点" を持たせる**
   → Critic Agent のような「**わざと粗を探す**」ロールを設計する

4. **評価基準を成果物の一部として扱う**
   → 「どう評価するか」自体が、プロジェクトの設計品質を決める

5. **講座でアピールできる差別化ポイント**
   → 「マルチエージェントを使った」だけの人は多い。「**評価設計の構造的限界に気付き、Critic Agent や卓越基準を設計し直した**」と言える人は希少。これは強力な差別化。
