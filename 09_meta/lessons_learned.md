> このプロジェクトを通じて発見した**「次回に活かす学び」「失敗とその原因」「うまく行った仕組み」**を時系列で蓄積。
> 後から自分が読み返したとき、または同じ手法で別プロジェクトに取り組むときに、知見を再利用できることが目的。
>
> **追記方針**:
> - 試行錯誤・気付きがあったら**即記録**(忘れる前に)
> - 「なぜそうしたか」「結果どうなったか」「次はこうする」のセットで書く
> - 失敗も成功も両方記録

## 2026-05-05:プロジェクト初版完成

### 🟢 うまく行った仕組み

#### 1. 9カテゴリ40+ファイルの企画書構造化
- **何をしたか**: ブランド/戦略/デザイン/ページ/技術/コンテンツ/エージェント/ワークフロー/メタの9階層に分類
- **結果**: AI が必要な情報だけ読みに行ける設計になり、トークン効率と一貫性を両立
- **次回への学び**: この構造はそのままテンプレート化できる(`09_meta/structure_review.md` 参照)

#### 2. Claude Design でビジュアル方向性を最初に確定
- **何をしたか**: コーディング前に Claude Design で 3パターン生成 → 1案選定 → スライダー微調整
- **結果**: ブランドの視覚的ゴール「Split Composition / NATURE × BODY」が確定し、その後の Designer / Coder 工程でブレが激減
- **次回への学び**: **視覚的ゴールを最初に固める**のは、AI 任せの開発でも非常に有効

#### 3. DECISION_NOTES.md で重要決定の経緯を記録
- **何をしたか**: 採用案・不採用案・採用理由・不変制約をすべて1ファイルに記録
- **結果**: Designer Agent が「なぜこの方向性か」を理解した状態で動けた
- **次回への学び**: **「不変ルール」を1枚のドキュメントにまとめる**ことが、複数エージェントの羅針盤になる

#### 4. self_refine_criteria による自己採点ループ
- **何をしたか**: Designer / Coder / Reviewer に5項目×10点の自己採点を義務化
- **結果**: 全12ページが平均44.6/50で一発合格、再実装ループ回避
- **次回への学び**: 評価基準を**実装着手前に明示**することで、品質下限を担保できる

### 🔴 失敗・反省

#### 失敗1: 章番号フォントサイズの初期指示ミス
- **何が起きたか**: Designer Agent への修正プロンプトで「章番号は現状のままでOK(意図的に小さく抑えている)」と明示してしまった
- **結果**: 修正サイクルが余分に1往復必要になった(章番号が小さすぎる問題が後で発覚)
- **原因**: 「変えるな」と書く前に、**変えないことの根拠を確実に検証していなかった**
- **次回はこうする**: AI に「変えるな」と指示するときは、**変えないことの根拠が確実か**を必ず疑う。「現状OK」と書くと、AI は判断を放棄する

#### 失敗2: 画像候補の事前収集が無駄になった
- **何が起きたか**: 画像36枚を事前収集 → ★マーキング作業(約30分)
- **結果**: Designer Agent が文脈の中で別の画像を選び、ユーザーは Designer Agent の選定を採用。事前収集は基本的に使われなかった
- **原因**: AI が選定するフェーズの前に、人間が「素材を絞り込む」のは情報損失を生む
- **次回はこうする**: **AI に先に選ばせ、不満があれば候補を提示する順**で進める。事前の人間絞り込みは最小限に

#### 失敗3: hotlinked Unsplash 画像の404
- **何が起きたか**: Designer Agent のモックで Unsplash の URL を hotlink 参照していた
- **結果**: 1枚(SUPPLEMENTS用)が Unsplash 側で削除されており、ローカルにダウンロードしようとして404エラー
- **原因**: 外部サービスの画像URLは**いつ消えるか分からない**
- **次回はこうする**: **最初からローカルにダウンロード**して保存する前提で進める。hotlink は仮置きであっても危険

#### 失敗4: 評価基準の範囲が狭かった
- **何が起きたか**: Reviewer Agent が44.6/50で合格判定を出した成果物に、外部レビューで多数の改善点が見つかった
- **原因**: 評価基準が「コード品質・パフォーマンス・a11y・レスポンシブ」だけで、トラスト要素・初見ユーザー視点・コンバージョン誘導が含まれていなかった
- **次回はこうする**: **Critic Agent を新設**して、業界ベンチマーク視点でのレビューを必須化。評価基準を「合格基準」と「卓越基準」に2層化(`08_workflow/self_refine_criteria.md` 改訂版参照)

#### 失敗5: orchestrator への数値指示の落とし穴
- **何が起きたか**: 第2バッチで「残り8ページ」と指示したが、実際は9ページ(SERVICES一覧を見落とし)
- **結果**: orchestrator が「実際は9ページですよ」と訂正してくれた(結果オーライ)
- **次回はこうする**: 数値を含む指示は、**明示リストで列挙**する(「8ページ」ではなく「ページ名9つを列挙」)

### 💡 メタ的な気付き

#### 気付き1: 「AIに任せれば自動的に高品質になる」は幻想
- **詳細**: Reviewer Agent の自己採点と外部レビューに大きな乖離があった
- **なぜか**: 評価基準・ロール・スコープ・インセンティブ・入力情報のすべてが「外部視点」を欠くと、AI の自己採点は身内採点になる
- **対策**: Critic Agent 追加、卓越基準の分離、視覚検証の組み込み、複数視点の組み合わせ
- **詳細解説**: `09_meta/final_review.md` 第五部、`memory/evaluation_design_principle.md`

#### 気付き2: トークン効率とファイル構造の関係
- **詳細**: Designer Agent が1回起動で約50,000トークン消費、これが複数回走る
- **原因**: 必読ファイルが多すぎる(23ファイル/2,453行)+ 重複が多い(料金が7ファイル、カラーが5ファイルに分散)
- **対策**: `00_QUICK_REF.md` 新設、`00_agent_briefs/` 新設、SSoT 化、_common.md 拡張
- **推定削減効果**: 約60%のトークン削減
- **詳細**: `09_meta/structure_review.md`

#### 気付き3: 課題作品としての完成度より、メタ学習が価値ある
- **詳細**: 「ALPS LABを完成させた」より「AI 開発の運用パターンと盲点を発見した」のほうが、講座の本質的な学びとして大きい
- **次回への学び**: 完成物そのものよりも、**プロセス・気付き・改善案**を成果として残す方が、次の100プロジェクトに活きる
